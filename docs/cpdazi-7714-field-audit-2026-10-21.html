01接收端到底要求什么

7714 的「要求」分三层：信封校验（硬性，错一条整个 socket 报错）、 value 形状（硬性）、业务字段（软性，读不到就补默认值）。 最后一层才是「缺字段」最容易出问题的地方——因为不报错，只是悄悄变成 0 / false。

1.1 硬性校验：信封 14 个键

键App 是否发接收端怎么校验
type / protocol_version发必须为 item_update / 2，且与 socket 路径 kind、name 一致
session_id发必须等于本次 manifest 里的 session；不一致 → envelope/path mismatch
kind / name发必须与 URL 的 /json/{session}/{name} 一致
manifest_revision发记录用；以接收端自己的 revision 为准
stream_handle发与 manifest 分配一致
schema_version发当前固定 1
sequence发同一流必须严格递增（≤ 上一帧就抛 stale v2 sequence，socket 出错）
source_timestamp_ms发非负整数（不校验单调）
sent_at_ms发非负整数
present发必须是 boolean
value发键必须存在；present=true 时须为对象（lane_ahead 为对象数组），present=false 时必须为 null
reason发仅 absent 时必填：非空字符串、长度 ≤ 64
关键点：接收端把「不认识的字段」直接忽略，但把「缺键 / 类型错 / 序列倒退」当协议错误。 所以「多发的键」无害（App 里的 lane_count、recommended_lane、lanes[]、lane_source、灯里的 valid 都属此类）， 「少的键」则会被静默补默认值。

04问题清单

点标题展开证据与建议。可按判定筛选。

A高德 4/5（左前/右前方）被映射成 CP 的「匝道」动作 102/101可疑
现状
AmapManeuver.kt：4 → 102、5 → 101、65 → 102、66 → 101。
冲突
CP _update_tbt()：102/105/112/115 = ("off ramp","slight left")。普通「靠左行驶」并不等于下匝道，CP 会在仪表上显示 off-ramp。
建议
普通分岔用 fork 家族（7/44/17/75/76/118 = fork-left，6/43/73/74/123/124/117 = fork-right）；只有确实 SEG_ASSISTANT_ACTION 表明匝道时才用 101/102。
B高德 6（左后方）→ 17（fork-left），而 7（右后方）→ 19（sharp right），左右不对称可疑
现状
同一步语义，右侧用了 sharp right（19），左侧却落到 fork 家族（17）。
冲突
CP 有 16 = ("turn","sharp left")，正好对应「左后方」。源码注释也承认这是「方向同侧但不够精确」的待核准项。
建议
拿到一条真实 10001/10006 左后方广播样本后改成 16；在此之前不建议盲改（现有 17 至少方向正确）。
C环岛「进入 / 驶出」都落到 rotary slight right（131 / 132），无法区分可疑
现状
AMap 11 → 131、12 → 132；CP 两者都是 ("rotary","slight right",5)。
影响
只影响仪表文字/图标提示，不影响 xTurnInfo=5；但「进入」与「驶出」在 CP 侧无法区分。
建议
低优先。若需要区分，应先确认 CP 是否有可用码（132/140/141 同为 slight 家族），否则保持现状。
Dlane.available[] 从未发送（isAvailable 在发送侧从未被赋值）缺失
现状
NaviDataModels.kt:368 要求「所有车道 isAvailable != null 才写 available」， 但 NaviStreamManager 构造 LaneItem 时只填了 index/direction/isRecommended/driveWayNumber/…， isAvailable 恒为 null → 该键永不出现。
影响
CP cluster_renderer 用 available 给车道条着色；恒空时全部按默认色画，推荐车道高亮没有依据。
建议
高德 13012 若确有逐车道可用/推荐标志，先补一条 laneInfo.available 桥接再发；不要把 isRecommended 直接当 available（推荐 ≠ 可通行）。
Eroute.polyline 恒为空数组缺失
现状
RouteData.polyline 默认 emptyList()，发送侧从未注入点列。
影响
CP _route() 拿到 0 点 → navi_points 无几何；任何依赖路线形状的消费都没有数据。
边界
不能用模型曲线、REST 另算路线、或「转向距离拼线」冒充当前车机路线；必须是当前选中路线的真实点列（最高 256 点）。
Fspeed.sdi 的「未知」被写成 0，两种写法混用可疑
现状
distance_m=0、speed_limit_kph=0、block_*=0 显式发送，而 section_type 是整键省略。
影响
CP _update_sdi：xSpdDist = nSdiDist，距离 0 意味着「已在摄像头处」（仅当 nSdiSpeedLimit > 0 时生效）。若 type 有效但距离未知，属于把未知变成最坏值。
建议

05优先级建议

优先级事项为什么值得先做改动面
P0L：车端灯色无秒数时 CP 清空 TrafficLight当前 CAN 相位主要价值被丢弃；需先确认跨端契约，是「功能是否生效」级别CP 侧 1 处判断 / 或 App 补秒数策略
P0② reason 空串兜底一个空串就能让整条 socket 报错，代价极低App 1 行
P1F：sdi 未知距离写 0可能被 CP 当成「已在摄像头处」，影响减速提示App 1 个门槛
P1N：section 限速 0 时两侧结论不一致避免「App 认为在区间内、CP 认为不在」App 1 个条件
P1A / B：转向码 4/5/6 语义偏差仪表动作提示错误，且属于「合法码错语义」最难现场发现码表 + fixture
P2D：lane.available 从未发送推荐/可用车道在仪表上没有着色依据需先确认 13012 字段
P2K：traffic_signal.source 语义排查灯态来源时会误判跨端确认后 1 行
P2E / G：polyline、off_route缺源，先取证再谈接线，禁止伪造取证为主
P3①③④⑨⑩：常量合并、virtual_gps、磁罗盘、app_status、风格统一契约卫生，不影响当前功能小改
红线：C/D/E 三条（逐车道可用性、路线几何、偏航状态）都没有已验证来源。 历史上最容易犯的错就是「为了凑字段而伪造」——例如把推荐车道写成 available、把模型曲线当 polyline。 本报告建议继续保持撤销，直到有真实广播样本。
