# Popusign (a800 LED) BLE 协议逆向分析报告

基于 Popusign APP HCI 抓包数据逆向分析（2026-06-04）。

**设备**: a800 LED 点阵屏 (96x16 像素) / 型号 GL1696H

---

## 1. BLE 连接信息

### GATT 服务

| Handle | 属性 | 用途 |
|--------|------|------|
| `0x0003` | WRITE_CMD (0x52) | **App → 屏幕** 发送协议数据 |
| `0x0005` | NOTIFY (0x1B) | **屏幕 → App** 回复/状态上报 |
| `0x0006` | CCCD | 启用 Notification (写 `01 00`) |

### 连接参数

| 参数 | 值 |
|------|-----|
| MTU | 512 (客户端请求 512, 服务端确认 512) |
| Write 类型 | WRITE_NO_RESPONSE (opcode 0x52) |
| 数据特征句柄 | `0x0003` |
| 通知特征句柄 | `0x0005` |

### BLE 协议格式 (关键发现)

> **写入和通知使用完全相同的格式**, 没有前导 `0x00` 字节。

```
[seq(1B)] [remaining_len(1B)] [payload...]
```

其中 `payload` 格式与 UART 0x5E 协议的内核一致：

```
payload = [type(1B)] [cuid_lo(1B)] [cuid_hi(1B)] [content...]
```

| 字段 | 长度 | 说明 |
|------|------|------|
| `seq` | 1B | 序列号, 每发送一帧递增 |
| `remaining_len` | 1B | payload 长度 = 3 + content 长度 |
| `type` | 1B | `0xCD`=命令, `0xDA`=数据, `0xE0`=错误 |
| `cuid` | 2B (LE) | 循环唯一 ID, 流控和确认用 |
| `content` | 可变 | 命令参数或数据内容 |

> 0x5E 帧头 (`0x5E`, 随机数, Length, 异或校验, CheckSum) 由 BLE IC 内部自动处理, APP 只需发送裸载荷。

## 2. 协议工作流

### 启动流程 (时序)

```
APP                                     屏幕
 |                                        |
 |--- 0x0003: D702 请求设备信息 ---------->|
 |                                        |
 |<-- 0x0005: D702 设备信息上传 -----------|
 |          (model=GL1696H, 固件版本)      |
 |                                        |
 |--- 0x0003: D602 请求节目列表 ---------->|
 |                                        |
 |<-- 0x0005: D602 节目列表上传 -----------|
 |                                        |
 |--- 0x0003: 0A01 EA 读取播放参数 ------->|
 |                                        |
 |<-- 0x0005: 0A01 播放状态上报 ----------|
 |                                        |
 |--- 0x0003: C002 00 获取设备参数 ------->|
 |                                        |
 |<-- 0x0005: C002 设备参数上报 ----------|
 |                                        |
 |  ===== 资产上传循环 (每张内容重复) =====  |
 |                                        |
 |--- 0x0003: D001 开始资产下载 ---------->|
 |          (UUID, 长度, 起始CUID)         |
 |                                        |
 |--- 0x0003: DATA 资产数据分片 ---------->|
 |          (160B/片, 可多片)              |
 |                                        |
 |--- 0x0003: DATA ACK (CUID=0空帧) ----->|
 |                                        |
 |<-- 0x0005: C081 资产接收确认 ----------|
 |          (包含资产 UUID)               |
 |                                        |
 |--- 0x0003: ED01 节目编辑 -------------->|
 |          (引用资产 UUID)               |
 |                                        |
 |  =====================================  |
 |                                        |
 |--- 0x0003: 0E01 01 显示开 ------------>|
```

### 播放控制 0x0A01 参数格式

APP 通知端上传的播放状态 (seq=108)：

```
01 0A 53 00 06 84 D6 93 33 00 30 05 00 01 02
 |  |  |     |              |     |  |
 cmd=0x01 mode=0x53 节目列表相关  播放序号参数
        loop=单循环
```

## 4. 关键命令详解

### 4.1 D001 — 资产下载

启动一个资产传输会话。资产通过 UUID 唯一标识。

**请求格式** (App → 屏幕):

```
args: [length(4B LE)] [start_cuid(2B LE)] [uuid(6B)]
```

| 字段 | 长度 | 说明 |
|------|------|------|
| `length` | 4B LE | 资产数据总长度 (字节) |
| `start_cuid` | 2B LE | 后续 DATA 帧的起始 CUID |
| `uuid` | 6B | 资产唯一标识 |

**示例**:
```
D001: length=351 start_CUID=0 UUID=63A5FD020030
```

### 4.2 DATA — 资产数据分片

资产数据通过多个 DATA 帧传输, 每帧最大约 160B (受 MTU 限制)。

**格式**:

```
content: [uuid(6B)] [asset_type(1B)] [payload...]
```

| 字段 | 长度 | 说明 |
|------|------|------|
| `uuid` | 6B | 资产 UUID (与 D001 一致) |
| `asset_type` | 1B | `0x00`=文本, `0x01`=位图, `0x02`=字体, `0xFF`=彩色图片 |
| `payload` | 可变 | 资产内容 (格式取决于 type) |

**ACK 机制**: 当一个资产的所有 DATA 帧发送完毕后, APP 发送一个 CUID=0 的空 DATA 帧作为 ACK。屏幕随后以 C081 通知回复该资产的 UUID 以确认接收。

### 4.3 ED01 — 节目编辑

将资产引用绑定到节目位。

**格式**:

```
args: [group(1B)] [program(1B)] [sub_count(1B)] [sub_elements...]
```

**子元素 (type=0x00 — 资产引用)**:

```
[type(1B)] [padding(7B)] [uuid(6B)]
```

| 字段 | 长度 | 说明 |
|------|------|------|
| `type` | 1B | 固定 `0x00` 表示资产引用 |
| `padding` | 7B | 全部为 `0x00` |
| `uuid` | 6B | 关联的资产 UUID |

**示例**:
```
ED01: 组0 节目7 1个子元素 [0] type=0x00 UUID=63A5FD020030
```

### 4.4 C081 — 设备状态通知

屏幕主动向 APP 上报状态。确认资产接收。

**格式**:

```
content: [state(1B)] [flags(1B)] [program(1B)] [uuid(6B)]
```

| 字段 | 长度 | 说明 |
|------|------|------|
| `state` | 1B | `0x80`=播放中/正常 |
| `flags` | 1B | `0x01` |
| `program` | 1B | 节目号 |
| `uuid` | 6B | 关联的资产 UUID |

**示例**:
```
C081: state=0x80 program=7 UUID=63A5FD020030
```

### 4.5 D702 — 设备信息

**设备信息上传** (屏幕 → App):

```
content: [cmd=0xD702] [model(8B)] [reserved] [ver_major] [ver_minor] [ver_patch] [width(2B LE)] [height(2B LE)]
```

**示例**:
```
model=GL1696H  v?.?.?  (?x? 像素)
```

### 4.6 0E01 — 显示开关

**格式**:

```
args: [0x00=关 / 0x01=开]
```

### 4.7 C002 — 设备参数控制

```
args[0]=0x00: 获取所有参数
args[0]=0x01: 设置参数
  args[1]=参数ID (0x01=旋转, 0x02=定时关机, 0x03=密码, 0x04=屏幕开关, 0x05=亮度)
  args[2]=参数值
```

### 4.8 C055 — 设备系统控制

```
args=[0x01, cmd]
cmd=0xF1: 重启
cmd=0xF2: 清空节目
cmd=0xFE: 格式化Flash
```

## 5. ACK 与流控

### ACK 帧

当 payload 长度为 3 (只有 type + cuid, 无 content) 时, 表示这是一个 ACK, 确认收到对应 type + cuid 的数据帧。

```
[type(1B)] [cuid_lo(1B)] [cuid_hi(1B)]
```

**双向使用**: App 向屏幕发送 ACK (如 CUID=0 的空 DATA 帧), 屏幕也向 App 发送 ACK。

### 重传机制

协议规范: 下行传输未及时收到 ACK 时, 将重发一次。

## 6. 与 iPixel 协议的对比

| 特性 | iPixel Color | Popusign (a800) |
|------|-------------|-----------------|
| 数据格式 | 自定帧格式 (`[总长LE16][命令码][参数]`) | 0x5E 协议内核 (`[type][cuid][content]`) |
| BLE 帧头 | 无额外帧头 | 无 0x5E 帧头 (BLE IC 内部处理) |
| 写入句柄 | `0xFA02` | `0x0003` |
| 通知句柄 | `0xFA03` | `0x0005` |
| 资产 UUID | 无 (使用页码) | 6字节 UUID 标识每项资产 |
| 工作流 | 直接数据传输 | 资产上传 → 节目引用 |
| 确认机制 | 固定格式确认帧 | CUID 流控 + C081 状态通知 |
| ACK | 5 字节固定回复 | 空 DATA/CMD 帧 (type + cuid, 无 content) |

## 7. 发送流程总结

要在 a800 LED 屏幕上显示内容:

1. **连接 BLE** → 启用 Notification (写 CCCD `01 00`)
2. **初始化**:
   a. 设置亮度 (`C002 param=0x05`) + 屏幕开启 (`C002 param=0x04`)
   b. 请求设备信息 (`D702`) — 可选
   c. 设置涂鸦/画板模式 (`C001 state=0x03`)
3. **上传资产**:
   a. `D001` — 指定 UUID 和总长度
   b. `DATA` ×N — 分片上传资产内容 (UUID + type + payload)
   c. `DATA ACK` — CUID=0 空帧标识结束
4. **编辑节目**: `ED01` — 引用资产 UUID
5. **播放**: `0A01` — 播放节目 (必须, 否则不显示)
6. **关闭**: `C002 param=0x04 value=0x00` 或 `0E01 00`

> 官方 APP 使用 `0E01`/`0E02` 旧式命令控制显示/亮度；
> 新推荐使用 `C002` 设备参数控制 (param=0x04 屏幕开关, 0x05 亮度), 在所有设备状态下均有效。

## 8. 资产数据格式 (结构化文本布局)

基于官方 APP HCI 抓包逆向分析. a800 不接受原始 1bpp 位图, 而是使用**结构化文本布局**格式:

```
[UUID(6B)] [type=0x01] [header(17B)] [embedded_UUID(6B)]
[metadata(8B)] [sub-elements(24B)] [color_element(6B)]
[text_element: 22 00 len_LE 2A UTF8_text]
[post-text_header(8B)] [char_count(4B)] [x-pos_table(4B×4)]
[per-character_data...]
```

### 8.1 颜色

RGB565 LE, 位于 `pl[60-61]` (payload 内偏移, 即 template[67-68]):

| 颜色 | RGB565 (LE) |
|------|-------------|
| 红   | `00 F8`     |
| 绿   | `E0 07`     |
| 蓝   | `1F 00`     |
| 白   | `FF FF`     |

### 8.2 动画控制

位于 `raw[44-47]` (即 template[47]), 格式 `02 00 03 XX`:

| XX 值 | 动画效果 |
|-------|----------|
| `0x00` | 静态     |
| `0x23` | 左移     |
| `0x21` | 右移     |
| `0x42` | 闪烁     |

> **注意**: 动画字节不在 template[30] (属 canvas width) 或 template[95] (`2C` 参数控制其他功能, 不是动画控制).

### 8.3 文本元素

格式: `22 00 [len_LE] 2A [UTF-8]`

- `22 00` = 文本元素标识
- `len_LE` = 文本总长度 (2B LE), 包含 `2A` 前缀
- `2A` = 星号前缀 (固定)
- UTF-8 文本: 实际渲染的文字内容

### 8.4 逐字符条目

每个字符条目格式:

```
[10 00 10 00] [03 00 width_LE] [width×2B 列优先位图]
```

| 字段 | 长度 | 说明 |
|------|------|------|
| `10 00 10 00` | 4B | 16×16 像素单元标记 |
| `03 00` | 2B | 宽度声明头 |
| `width_LE` | 2B (LE) | 字符宽度 (列数), bitmap 数据长度为 width×2 |
| bitmap | width×2 B | 列优先位图, 每列 2 字节 (上下半行) |

> ⚠️ **关键**: `width` **必须等于** bitmap 的实际列数. 
> 如果声明 width=6 但提供 28B 位图, 设备只读 12B 后将剩余 16B 误解析为下一条目, 导致全乱.

**固定模板**: 每个字符 36B = 8B 头 + 14列×2B = 28B 位图, 最多 4 字符.

**变长格式**: 官方 APP 根据实际字符宽度动态调整条目大小:
- "A" (1 字符): 130B 总
- "AB" (2 字符): 168B 总
- "你好" (2 字符): 176B 总
- "*向左移动" (4 字符): 260B 总

### 8.5 x-位置表

位于 `pl[93-108]` (template[100-115]), 4 个 LE32 值, 每个字符一个.
